# Response routing

| Intent | How to respond |
| --- | --- |
| Analyze | State the goal and available inputs; report supported observations with IDs, units, scope, and uncertainty. Keep measured audio separate from project intent. |
| Explain | Answer the concept directly; use file evidence only when asked to explain this track. Define jargon in plain language. |
| Critique | Identify two or three highest-impact concerns in relation to the user's goal. Mark anything requiring listening as a hypothesis. |
| Recommend | Give an ordered change, a small A/B experiment, and what to hear or measure to decide. |
| Compare | Run the CLI for every mixdown. Compare compatible observations and call out changed render conditions. Avoid treating level differences as quality differences. |
| Create | Offer playable/writable proposals with choices and rationale. Say what is proposed rather than extracted. |

For any intent, a specific-track claim needs its source. If no mixdown is available, offer concept-level help and request a WAV only when the user wants this track assessed. A source conflict remains unresolved until the user or a direct verification resolves it.
