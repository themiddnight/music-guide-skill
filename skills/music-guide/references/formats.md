# Input format contract

| Flag | Accepted content | Bound | Evidence |
| --- | --- | --- | --- |
| `--mixdown` | Optional audio that libsndfile decodes: WAV, RF64, W64, AIFF, FLAC, CAF, OGG Vorbis/Opus, MP3 | 4 GiB, 6 hours, peak magnitude up to 1e6 (+120 dBFS) | Format, duration, channels, sample rate, sample peak, RMS, crest factor, full-scale sample count, integrated/momentary/short-term loudness, LRA, true peak, short-term loudness timeline, band energy, spectral centroid, stereo correlation and side-to-mid ratio, pitch-class profile, inferred tempo and key candidates |
| `--stem` | Same as `--mixdown` | Same as `--mixdown`, each | Same measurements, independent source scope |
| `--midi` | SMF 0/1 with ticks per quarter note | 4 MiB each | Tempo and meter maps, static tempo/meter for constant files, track names, per-track note summaries (flagged `percussion` when every note is on General MIDI channel 10); paired notes with `--detail full` |
| `--solna` | JSON formatVersion <= 12 with validated inspected fields | 8 MiB each | Stored BPM, meter ID, loop scale IDs and chords |
| `--dawproject` | ZIP with one stored or deflated project.xml and an optional metadata.xml | 64 MiB archive, 8 MiB XML, 16384 entries, 8 MiB central directory; members that are not read are not size-bounded | Project version, application, metadata, transport tempo/meter, tempo and meter automation, tracks with plugins, clip counts, notes, markers and media basenames |
| `--project` | Any project file or package; the format is detected from the extension and content signature | Per format in `formats.py` | Parsed evidence for a supported format; otherwise an inventory with format-specific export guidance |
| `--declarations` | JSON array under declarations schema | 8 MiB | User supplied static facts |
| `--detail` | `summary` (default) or `full` | At most 50,000 listed notes per source | `full` adds one observation per stored note |

At least one of `--mixdown`, `--stem`, `--midi`, `--solna`, `--project` or `--dawproject` is required; declarations alone are not enough. Without a mixdown the report carries a `no_mixdown` info diagnostic, because the rendered sound is unknown. A supplied mixdown that cannot be read is still fatal.

Shared bounds keep hostile files from exhausting memory or flooding the report. Every XML parse refuses more than 2,000,000 elements or nesting deeper than 256. Each project source reports at most 5000 tracks, plugins, markers and media references, with one `project_list_truncated` warning per capped property. MIDI tempo, meter and track-name lists are capped at 5000, and unmatched note-ons or note-offs become one counted diagnostic per track. Stored tempo is accepted from above 0 up to 1000 BPM, and meter from 1 to 999 beats over any whole denominator from 1 to 128, so irrational meters such as 4/3 or 7/5 are kept. A value outside these ranges, or a meter that is not made of whole numbers, is skipped with one `implausible_value` warning that names the property, the value and its location; the rest of the project is still reported. A tempo map drops only its implausible points and warns once with a count. Any unexpected failure inside an optional source becomes that source's `optional_source_error`, so the rest of the report survives.

`--project` accepts these formats. A directory package must be passed as the directory. An extension whose content does not match the format's signature is reported as a source error rather than guessed. An unknown extension is inventoried with generic export guidance.

Parser bounds live in `scripts/music_guide/adapters/common.py`; each format's byte limit is its row in `scripts/music_guide/formats.py`. The DAWproject parser reads only `project.xml` and an optional `metadata.xml`, and rejects DTD, entities, and external references. MIDI tempo and meter events are reported as `midi.tempo_map` and `midi.meter_map` lists of `{tick, beat, ...}` entries. Only when a file has exactly one `set_tempo` event across all tracks, at tick 0, does it also produce a static `tempo` claim (method `midi-constant-tempo`); a single `time_signature` at tick 0 likewise produces a static `meter` claim (method `midi-constant-meter`). A changing or late tempo is never reduced to a static claim, because the SMF default before the first event is not evidence. Compare declarations against such maps by hand. No source can establish rendered sound except the supplied audio samples, and the CLI does not infer timbre or meaning from them.

DAWproject transport tempo requires an explicit `unit="bpm"`. Other units and missing units are rejected rather than guessed. A missing `Structure` produces no track-count claim. An explicitly empty `Structure` has a count of zero. Automatic conflict detection compares shared static tempo and meter claims with matching scopes and units whose provenance is measured, extracted, or user declared. Inferred estimates never raise automatic conflicts. Tempo values within 0.01 BPM count as equal because MIDI stores whole microseconds per beat (92 BPM reads back as 91.99999 BPM). Meter must match exactly. Other properties and event maps require explicit human comparison.

## Logic Pro and GarageBand packages

Sources: the observed `.logicx` layout of Logic Pro 12.4 and the [MultimediaWiki GarageBand page](https://wiki.multimedia.cx/index.php/GarageBand). GarageBand 10.0.3 and later uses the same package layout as Logic Pro.

The adapter reads only `Resources/ProjectInformation.plist` and each `Alternatives/NNN/MetaData.plist`, as XML or binary property lists of at most 4 MiB. It never opens `ProjectData` (undocumented binary), `Media/` files, or any path a plist lists. A symbolic link at any step of a read path, or a plist that is not a regular file (for example a named pipe), rejects the whole package. Numeric plist fields accept an integral float such as `44100.0`. A package without a readable `MetaData.plist` (older GarageBand, iOS GarageBand) is an error with export guidance.

- `project.application` comes from `LastSavedFrom`. A package with one alternative reports it at `project` scope, so its tempo and meter meet MIDI, DAWproject and declaration claims. With several alternatives each is its own scope, `alternative:NNN`, named by `VariantNames` in `logic.alternative_name` (`garageband.*` for `.band`); compare a declaration against one with that scope, for example `alternative:000`.
- `tempo` (`BeatsPerMinute`), `meter` (`SongSignatureNumerator` and `SongSignatureDenominator`), `project.key` (`SongKey` and `SongGenderKey`, joined as "D minor"), `project.sample_rate` and `project.track_count` (`NumberOfTracks`) are stored settings per alternative. The tempo is the project start tempo; a tempo map in `ProjectData` is not read. Logic stores a key even when the user never set one, so treat `project.key` as stored intent. A key with only one half present is reported as `logic.partial_key` instead.
- `project.media_reference` lists basenames from `AudioFiles`, `UnusedAudioFiles`, `PlaybackFiles`, `SamplerInstrumentsFiles`, `QuicksamplerFiles`, `ImpulsResponsesFiles` and `UltrabeatFiles`; the list name is the end of the locator and `logic.media_list` carries the role and path count. `logic.bundled_media` counts regular files under `Media/` by name only; links are counted but not followed, every entry including directories counts toward the 50,000-entry walk cap, and a `Media` that is a link or not a directory is skipped with the warning `bundled_media_skipped` instead of rejecting the package.
- Not extracted: track names and kinds, regions, MIDI notes, plugins, tempo and meter changes, markers. An info diagnostic `project_data_not_read` says so.

## LMMS projects

Sources: LMMS 1.2.2 `DataFile.cpp`, `Song.cpp`, `Track.cpp`, `Note.cpp`, `MidiTime.h`, `AutomatableModel.cpp` and `MidiExport.cpp`, the LMMS 1.3 clip renames in `DataFile.cpp`, and the 1.2.2 demo projects.

LMMS parses a file as XML first and falls back to `qUncompress`, so the adapter does the same: an `.mmpz` is a 4-byte big-endian length followed by a zlib stream. Both the file and the inflated XML are limited to 32 MiB, inflation is bounded against zlib bombs, and a declared length over the limit is refused. LMMS writes a bare `<!DOCTYPE lmms-project>`; only that exact line is removed, so any other DTD or entity is still rejected. Detection needs `<?xml`, `<!DOCTYPE lmms-project`, `<lmms-project` or a valid zlib header after the length.

- `project.application` is `creator` plus `creatorversion`. `tempo` is `head/@bpm` and `meter` is `head/@timesig_numerator` over `@timesig_denominator`. When LMMS stores the tempo as a `<bpm>` element (automated or log-scaled) the value is the one at save time, the reason says so, and the warning `tempo_model_is_element` is added.
- Every `track` in the song container and, for beat/bassline tracks, every track in the nested pattern store becomes a `project.track` (type 0 instrument, 1 beat/bassline as group, 2 sample as audio, others unknown); `lmms.track_type` carries the type code, label and container. `project.plugin` lists instrument and effect names from tracks and from the mixer, `project.clip_count` counts the pattern, sample, beat/bassline and automation clips of a track, and `project.media_reference` lists `src` basenames of sample clips and instruments.
- Notes come from `note` elements in MIDI clips (`pattern`, or `midiclip` in 1.3). Ticks convert to quarter notes at 48 ticks per quarter (192 per whole note in every meter). The key convention follows LMMS's own file-version upgrades (`DataFile.cpp`, `UpgradeExtendedNoteRange.cpp`). Files with an integer `version` of 20 or more store MIDI note numbers (key 69 is A4) and the pitch equals the key. Older files, files with `version="1.0"` or none, store A4 as key 57 and the pitch is `key + 12`; the reason of `project.track_notes` and `lmms.pitch_convention` say which was used. A file with no readable version and no creator version is assumed old at low confidence, as LMMS itself does. Keys that land outside MIDI 0-127 are skipped with the warning `lmms_notes_out_of_range`. Base-note and master-pitch transposition are not applied. Velocity is `vol * 127 / 200`. A negative length marks a beat step note: up to file version 26 it takes the length LMMS's own upgrade assigns (`DefaultTicksPerBar / 16` = 12 ticks); from file version 27 a negative length is excluded with a warning because no length is confirmed. Positions inside a nested beat/bassline pattern are local to that pattern, not placed on the song timeline.
- Not extracted: automation values, the placement of beat/bassline clips on the timeline, sample rate (LMMS keeps it in its settings), instrument settings, and any embedded `data`.

## Ardour sessions

Sources: Ardour 5.12, 6.9 and 8.12 `session_state.cc`, `tempo.cc` and `libs/temporal/tempo.cc`, `location.cc`, `route.cc`, `playlist.cc`, `plugin_insert.cc` and `temporal/timeline.cc`, read from the Ardour GitHub mirror, plus Ardour forum reports of the Ardour 4 and older `start=` layout.

The adapter reads the session XML only (32 MiB limit, no DTD or entities). It never opens the session's audio, MIDI or plugin files. Three `TempoMap` layouts are read. Ardour 4 and older use flat `Tempo` and `Meter` children placed by `start="1|1|0"` (`beats-per-bar` names the meter numerator). Ardour 5 and 6 add whole-note `pulse` positions. Ardour 7 and later use `Tempos` and `Meters` lists with `quarters="beats:ticks"` positions and `npm`/`note-type` tempos. Inactive tempos are skipped. Tempo is converted to quarter notes per minute as `npm * 4 / note-type`.

- `project.application` is `ProgramVersion/@modified-with` (or `created-with`), `project.sample_rate` is `Session/@sample-rate`, and `ardour.session_version` is the file version.
- `project.tempo_map` lists every active tempo start. A single tempo also gives a static `tempo`, a single meter gives a static `meter`, and several meters give `ardour.meter_map`. Ramps are reduced to their starting tempo. A session with several tempos but no readable positions gets the warning `tempo_positions_unreadable` and no tempo claim.
- `Location` marks become `project.marker`; session, loop and range locations become `ardour.session_range`, `ardour.loop_range` and `ardour.range`. Positions are sample counts (divided by the session rate), `a<superclock>` (divided by the tempo map's superclock rate) or `b<ticks>` (1920 ticks per quarter). A location whose rate is missing is skipped with the warning `locations_skipped`, never defaulted, and a location without a start (or an end, for ranges) is skipped with the warning `locations_incomplete`. Position numbers have at most 18 digits. Sample rates outside 1,000 to 1,000,000 Hz and superclock rates outside 1,000 to 10^12 reject the session. A meter outside the shared ranges is skipped with an `implausible_value` warning. Several meters without readable positions give the warning `meter_positions_unreadable` and no meter claim.
- Each `Route` is a `project.track`: master, audio, MIDI or bus from `PresentationInfo/@flags` (the monitor section is `unknown`); `ardour.route` keeps the type, flags and active state. `lv2`, `ladspa`, `luaproc`, VST and AudioUnit processors become `project.plugin`; built-in processors do not. `project.clip_count` is the region count of the track's current playlist; unused playlists are not counted. `project.media_reference` lists `Source` names.
- Not extracted: MIDI notes (they live in separate `.mid` source files; the info diagnostic `ardour_notes_not_read` says so), automation, region positions, VCAs, and tempo ramp shapes.

## Add an adapter

1. Add a module under `scripts/music_guide/adapters/` with a function `adapter(path, source_id, evidence, detail)` that writes to the staged `Evidence` object. Use `dawproject.py` as a boundary example.
2. Register it as one `ProjectFormat` row in `scripts/music_guide/formats.py`: a unique name (also reported as the source adapter), label, extensions, `file` or `directory`, byte limit, signature check, adapter, and export guidance. Setting `adapter` on an existing inventory row upgrades that format.
3. Read containers with the bounded helpers in `common.py` (`_read_zip_member`, `_gunzip_bounded`, `_parse_xml`) and keep embedded media paths as `_media_basename` values only.
4. Record shared facts through `ProjectFacts` in `scripts/music_guide/project.py` so every application emits the same properties: `project.application`, `tempo`, `meter`, `project.tempo_map`, `project.sample_rate`, `project.key`, `project.track_count`, `project.track`, `project.marker`, `project.plugin`, `project.media_reference`, `project.clip_count`, `project.track_notes` and, with `--detail full`, `project.note`. Summarize notes with `notes.summarize_notes`. Use `Evidence.add` directly only for format-specific facts, with an exact locator, units, scope, time domain, provenance, and confidence reason.
5. Reject unsupported variants with an actionable `ValueError`. Normalize parser-specific failures at the adapter boundary. The CLI merges staged observations only after parsing succeeds.
6. Test a representative fixture, missing fields, malformed data, unsupported variants, and the copied skill. Update this contract only after those checks pass.

## Ableton Live sets and REAPER projects

Both formats are read as stored intent only. The adapters never open referenced media, load a plugin, or follow a path, and they keep embedded media paths as basenames. Both emit the shared `project.*` vocabulary: application, tempo, meter, tempo map, markers, tracks, plugins, media references, clip counts and per-track note summaries. An unreadable file becomes a `optional_source_error` and the rest of the report survives.

**Ableton Live (`.als`).** The file is gzip XML, decompressed with a 64 MiB bound. Application comes from the root `Creator`, and `ableton.version` keeps the schema attributes. Tempo comes from `Tempo/Manual` on `MasterTrack` (Live 11 and earlier) or `MainTrack` (Live 12). Tempo automation on that track becomes `project.tempo_map` in beats; a static `tempo` claim exists only when the automation holds one value or is absent, and the Manual value is kept as `ableton.manual_tempo` beside a changing map. Meter is decoded from the master `TimeSignature` integer code (4/4 is 201, 7/8 is 303), with confidence `low` because Ableton does not document the encoding. It falls back to explicit `TimeSignatures/RemoteableTimeSignature` Numerator and Denominator pairs, and meter automation becomes `ableton.meter_map`. Tracks are `AudioTrack`, `MidiTrack`, `GroupTrack`, `ReturnTrack` and the master, named from `EffectiveName` then `UserName`. Locators become beat markers. Third-party plugins become `project.plugin` entries named from `PlugName`, `Vst3PluginInfo/Name` or `AuPluginInfo/Name`. Every other device is reported separately as `ableton.device` with the XML element name and `builtin: true` (`false` for Max for Live `MxDevice*` elements); the element name is an internal tag, not the label shown in Live. A `PluginDevice`, `AuPluginDevice` or `Vst3PluginDevice` whose plugin name is empty is still third-party: it becomes a low-confidence `project.plugin` named for the element, with a reason that says the name is empty, and is never reported as built-in. Samples come from `SampleRef/FileRef` (`Name`, then `Path`, then `RelativePath`). A Live 12 `ScaleInformation` root and name becomes `project.key` with confidence `low`, because Live may store a default scale when Scale Mode is unused.

`project.clip_count` counts arrangement clips; session-view slot clips are counted in `ableton.session_clip_count`. MIDI note summaries use `Notes/KeyTracks/KeyTrack/MidiKey` with `Notes/MidiNoteEvent` `Time`, `Duration` and `Velocity`. Arrangement notes are positioned at the clip `CurrentStart` plus the note time relative to the clip start marker (`LoopStart + StartRelative`), limited to the clip's first pass, and reported as `project.track_notes` with confidence `medium`. Session-clip notes have no arrangement position, so they are summarized separately as `ableton.session_clip_notes` and `--detail full` lists arrangement notes only. Loops are not unrolled, muted notes are excluded, velocities outside 0 to 127 are clamped and counted in an `ableton_velocity_clamped` warning, and warping and tempo changes are not applied. A clip without readable loop and position fields is skipped and counted in the confidence reason. The sample rate is not stored in a set, so no `project.sample_rate` is produced.

**REAPER (`.rpp`).** The file is a text tree of `<TAG ...>` blocks closed by `>`. The reader follows REAPER's quoting (`"`, `'` or a backtick opens a string that ends at the next matching character, with no escapes), skips `|` text lines and long single-token data lines, and refuses files over 1,500,000 property lines, 64 levels of nesting, binary bytes, unbalanced blocks or an unterminated string. The header gives the application and `reaper.header`. `SAMPLERATE` gives the sample rate and `TEMPO` gives tempo and meter. Points in `TEMPOENVEX` (`PT position bpm ...`, positions in seconds) become `project.tempo_map` in beats by treating each point as a tempo step, so ramps are not interpolated. The third `PT` value is the point shape and only `1` (square) is a step: any other or missing shape adds a `reaper_tempo_ramps` warning and lowers the `project.tempo_map` confidence to `low`. Points at the same time keep file order. A static `tempo` claim follows the same rule as Ableton, with the `TEMPO` line kept as `reaper.base_tempo` beside a changing map. An envelope stored as inactive (`ACT 0`) is ignored with a warning, and time-signature changes on the envelope are not decoded. `MARKER` lines become `project.marker` in seconds; two lines sharing an index with the region flag become one `reaper.region`.

`TRACK` blocks give names, and `ISBUS 1` marks a folder; REAPER stores no track type, so every other track is `unknown`. Effects inside any `FXCHAIN`, `TAKEFX` or master chain (`VST`, `AU`, `JS`, `CLAP`, `DX`, `LV2`) become `project.plugin` entries named by their first argument. `ITEM` blocks give `project.clip_count`, and `SOURCE ... FILE` lines give media basenames from every take. Notes come from `SOURCE MIDI` blocks with `HASDATA 1 <ppq> QN`: `E` and `e` lines carry delta ticks and hex status and data bytes, paired by channel and pitch. Status must be a channel message (`80` to `EF`) with data bytes from 0 to 127; program change and channel pressure carry one data byte. An event that fails these checks is skipped and counted in a `reaper_invalid_midi_event` warning. Only the selected take is read, muted items are skipped, and note positions are the item `POSITION` converted to beats plus ticks over ppq. Source start offsets, item loops and tempo-ignoring sources are not applied, and notes past the item end are dropped. The confidence reason of `project.track_notes` reports these counts and whether a tempo map was integrated.

Parsing uses memory in proportion to the file; a 38 MB XML set with 500,000 notes peaks near 520 MB, and a 26 MB project with 1.2 million MIDI event lines near 565 MB.

Format uncertainty. No public specification exists for either format, and no real `.als` or `.rpp` file was available. The structures above come from the sources listed next, and the tests use fixtures built from them. Unverified points are the Ableton meter integer code, the exact clip start-marker and loop semantics, the location of `RemoteableTimeSignature` outside clips, the REAPER `TAKE SEL` convention, the `ACT` flag meaning, the clip `Disabled` field (no public source confirms it, so deactivated clips are still counted and their notes still read), and the sub-fields of `MARKER` and `PT` beyond those used here.

Sources: Ableton `.als`: github.com/offlinemark/dawtool (`dawtool/daw/ableton.py`: root attributes, `Tempo/Manual`, tempo envelopes by `PointeeId`, locators), github.com/jake-g/ableton-parser (`parse_projects.py`: `MasterTrack/DeviceChain/Mixer`, `Tracks/*`, `ScaleInformation`, `PluginDesc` infos, `SampleRef/FileRef`, `MainSequencer`), github.com/andrewcb/alsd (`alsd.py`: `Notes/KeyTracks/KeyTrack`, `MidiKey`, `MidiNoteEvent`, `Loop`, `CurrentStart`), pypi.org/project/daw-schemas (structural schema of Live 12 sets), help.ableton.com (numerator 1 to 99 and denominators 1, 2, 4, 8, 16; the shared bounds accept more). REAPER `.rpp`: github.com/Perlence/rpp (lexer quoting rules), github.com/CharlesHolbrow/rppp (`rpp-examples/midi-item.RPP`, `two-vst3s.RPP`: `HASDATA 1 960 QN`, `E` and `e` lines, `FXCHAIN` and `VST` blocks, `TEMPO`, `SAMPLERATE`, `ISBUS`).

Time domains in reports: `static` (one value for the scope), `midi_ticks` (positioned by MIDI ticks), `project_beats` and `project_seconds` (positioned in a project timeline), and `loop_sequence` (ordered inside a stored loop).

Do not launch a DAW, execute a plugin, decode proprietary data without a tested parser, or follow media paths as a shortcut. Ask for WAV, MIDI, stems, or an explicitly supported export instead.

## FL Studio, Studio One and Cubase

These three formats are undocumented, so each adapter records how far it was checked. No adapter loads a plugin, opens a media path or reads a file other than the project.

**FL Studio (`.flp`).** Reads the event stream (header `FLhd`, data `FLdt`, event IDs 0-63 byte, 64-127 word, 128-191 dword, 192-255 length-prefixed). Reports `project.application`, `tempo` (event 156, BPM x 1000, or the legacy whole-BPM event 66; confidence medium), `meter` (events 17 and 18, confidence low because the meaning is a single-source reading), channels as `project.track` with `flstudio.channel`, channel plugin and mixer slot names as `project.plugin` (FL hosts every VST or AU as `Fruity Wrapper`, so a wrapped plugin is named by its display name from event 203 at confidence low, or reported as `Fruity Wrapper` when no display name exists), sample basenames, `flstudio.pattern` and per-pattern `flstudio.pattern_notes` (confidence medium, beats are quarter notes inside the pattern), `flstudio.arrangement` playlist counts, and title, genre, artists and comments. Note pitch is FL's key number, which equals the MIDI note number (FL names MIDI 60 C5; reports name it C4). `--detail full` adds `flstudio.note` in the `pattern_beats` time domain, which is positioned inside a pattern, not on the arrangement timeline. Layout-dependent facts (`flstudio.channel`, tracks, plugins, counts, `flstudio.arrangement`) are medium or low, never high. The built-in Sampler channel (type 0) is `unknown` because it plays pattern notes, and a native or instrument channel with a sample and no plugin is `audio` (PyFLP's sample channel rule; an audio clip and a sampler cannot be told apart). The playlist item size follows the FL major version (32 bytes before 21, 60 from 21) and a playlist whose length does not divide by that size is skipped with a warning instead of guessed. A file with more than 1,000,000 notes is rejected. Not decoded: tempo automation, time markers, plugin state, which insert holds which slot, and where patterns sit in time. Sources: PyFLP documentation and source (pyflp.readthedocs.io), node-flp (github.com/andrewrk/node-flp). No real project was available, so tests use synthetic files.

**Studio One (`.song`).** A ZIP of XML read with `defusedxml`. `Song/song.xml` gives the tempo map (seconds per quarter note converted to BPM), time signature map, key signature map, tracks, marker track, arranger sections and per-track clip counts; `Devices/audiomixer.xml` gives insert plugin names, tied to a track through its channel UID; `Song/mediapool.xml` gives media basenames; `metainfo.xml` gives the generator (`project.application`), `Media:SampleRate` and `Media:KeySignature`. Every metainfo attribute is also recorded with its literal id as `studioone.metainfo`, and attributes that are not named above are never mapped to a shared property. A single tempo or meter segment at beat 0 becomes a static claim; longer maps stay as `project.tempo_map` and `studioone.meter_map`. Only an absent attribute is defaulted (a missing `start` is beat 0, and the reason or a `studioone_start_defaulted` diagnostic says so); a present attribute that does not parse skips that item with a `studioone_attribute_invalid` or `studioone_segment_dropped` warning. A dropped tempo or signature segment (non-positive, unparsable or over-1000 BPM tempo, or a meter outside the shared ranges) blocks the static claim and leaves a map. A `FolderTrack` is `folder`, and an insert slot with no device name is skipped. Another public reader reports that Studio One can write prefixes it never declares (`x:id`); this reader repairs that once, after a failed strict parse. Not decoded: instrument notes (`Performances/*.musicx`), automation envelopes, track kinds other than audio and instrument. Source: studio-one-mcp (github.com/NeanderthalMan/studio-one-mcp), whose reader was verified on songs saved by Studio One 5.5.2. No real song was available, so tests use synthetic archives in that shape.

**Cubase and Nuendo (`.cpr`, `.npr`).** A RIFF-like file with an extra `NUND` tag, then `ROOT`/`ARCH` chunk pairs. Structural and high confidence: application name and version from the `PAppVersion` object, the chunk list, and the media attributes in the `Metadata` chunk (`cubase.media_attribute`). `AudioSampleRate` also becomes `project.sample_rate` (medium) and `MusicalTempo` and `MusicalSignature` become `tempo` and `meter` at low confidence, because the tempo and signature tracks are not decoded. Track names, plugin names (`Plugin Name` attributes) and media file names are found by byte patterns in the object stream and are reported at low confidence with that reason; the track kind comes from the class reference stored before the track header, and is `unknown` when none is found. Metadata floats must be finite, `MusicalTempo` must lie in 1 to 1000 BPM and `AudioSampleRate` in 1000 to 768000 Hz (otherwise, including zero and negative values, a `cubase_value_out_of_range` warning, with the attribute still recorded). Plugin names include Cubase's built-in channel modules (Panner, EQ, Input Filter) and say so in their reason. The media name scan examines at most 20,000 candidates and reports a `cubase_scan_limit` warning when it stops. A failure in any deeper step leaves the application and adds a `cubase_deep_parse_failed` warning. Checked against one Cubase 11 project only. Sources: cbconv (code.volse.net/audio/cbconv) for the container layout.

## Scores, AAF and DAWproject details

**MusicXML** (`.musicxml`, `.mxl`). Partwise and timewise scores, plain or compressed (the rootfile named by `META-INF/container.xml`), up to 16 MiB of XML. The standard public DOCTYPE that exporters write is removed before parsing, so a DOCTYPE with an internal subset or any other external reference is still rejected. Each part is a track named by `part-name`. Beats are quarter notes from `divisions`. Chords share a start, `backup` and `forward` move the cursor, and `tie` chains merge into one note. Written pitch is converted to sounding pitch with `transpose`. Tempo comes from `sound/@tempo`, or from `metronome` marks only when no playback tempo exists (beat unit and dots are converted to quarter-note BPM). Key comes from `fifths` and `mode`, and only from non-transposing parts. Rehearsal marks become markers. Not read: repeats and jumps (never unrolled), grace notes, unpitched notes, `offset` on directions, per-note articulation, and the MusicXML dynamics model beyond a note's `dynamics` attribute. `sound/@dynamics` sets the default velocity of the notes after it until changed, and a note's own `dynamics` wins; both are a percentage of the default forte, which is MIDI velocity 90 (velocity = percent * 0.9, clamped to 1-127). A velocity placeholder of 90 stands in where none is stored: `project.track_notes` drops to medium confidence and its reason says `N of M velocities are placeholders`, `musicxml.velocity_placeholders` counts them per track, and the info diagnostic appears only when a note lacked a velocity. Numbers are parsed strictly (plain decimals of at most 18 digits, no exponents), so `1e400` is a source error. A `time` with several beats and beat-type pairs is skipped with a warning, fractional alters are rounded and counted (`musicxml_microtonal`), a pure octave transposition keeps the key, and a `backup` before the measure start is clamped and counted.

**MuseScore** (`.mscz`). A zip holding one `.mscx` (named in `META-INF/container.xml`, otherwise the only top-level `.mscx`). Notes use MuseScore's concert pitch, `durationType` plus dots, the stored `duration` fraction, and tuplet ratios from `Tuplet` and `endTuplet`. Ties come from `Spanner type="Tie"` with `next` and `prev`. Tempo is the stored beats per second times 60. Not read: repeats and jumps, grace notes, notes marked as not played, measure-repeat contents, and the older pre-3.0 tie encoding. MuseScore velocities are not read, so every note carries the placeholder 80 and `project.track_notes` is medium confidence with that stated in its reason and in `musescore.velocity_placeholders`. Fractions are parsed strictly (integers, decimals or `p/q` of at most 18 digits, no exponents), dots are limited to 16 and tuplets to 16 levels. The MuseScore file format is not formally specified, so the layout follows the open-source reader and was tested on synthetic files only.

**AAF** (`.aaf`, binary structured storage). pyaaf2 opens the file read-only inside a child process that is stopped after 60 seconds or 1.5 GiB, because pyaaf2 sizes buffers from counts inside the file. The child runs under `python -I` and receives the parent's absolute import path on stdin, so packages installed with `pip install --user` or a custom path stay importable; it ends itself with an alarm (and an address-space limit on Linux) even if the parent is interrupted. The parent polls the child's memory through `ps` where it exists (macOS does not enforce an address-space limit) and adds the info diagnostic `aaf_memory_cap_unavailable` when neither mechanism exists. pyaaf2 is imported only in the child, so it is required only when an AAF file is analyzed. Slots with a missing or zero edit rate are skipped and counted in the warning `aaf_slots_without_edit_rate`. The application is the latest Identification. Tracks are the sound and picture timeline slots of top-level composition mobs, with their edit rate and length in `aaf.slot`. Clip counts are source clips with a non-null source. Markers are comment or descriptive markers in event slots, converted to seconds. Media references are network locator basenames of source mobs. Sample rate comes from sound edit rates of 8 kHz or more and sound descriptors, and is reported only when they all agree. Container inconsistencies pyaaf2 logs become `aaf_container_warning` diagnostics. AAF stores no tempo or meter, so none is reported. AAF XML, OMF and embedded essence are not read.

**DAWproject**. A missing `Structure` still gives no track count. Tempo automation needs `unit="bpm"` and becomes `project.tempo_map` (beats). Time signature automation becomes `dawproject.meter_map`. Clip counts cover arrangement clips only (clips nested inside a clip are content, and scenes are ignored). Notes are placed on the arrangement in quarter-note beats: a clip's `time` and `playStart` anchor its content, notes outside the played window are dropped or cut at the clip end, and `contentTimeUnit="seconds"` content is converted with the stored tempo. Approximations: tempo ramps use the mean of the two segment tempos, tempo before the first automation point is the first value, loops are not unrolled (a diagnostic counts looped clips), and clips that reference shared content by id or time-warped note timelines are skipped with a warning. A missing note velocity becomes the placeholder 100: the affected track's `project.track_notes` is medium confidence, its reason says `N of M velocities are placeholders`, and `dawproject.velocity_placeholders` counts them. Linear tempo ramps always add the info diagnostic `dawproject_tempo_ramp_approximation`, and a track whose seconds-based content was placed through a ramp is medium confidence. Attributes above 1e15 and positions beyond 1e12 beats are source errors.

**Sources.** W3C MusicXML 4.0 reference (https://www.w3.org/2021/06/musicxml40/), MuseScore 3.6 reader sources (`libmscore/measure.cpp`, `chordrest.cpp`, `note.cpp`, `tempotext.cpp`), pyaaf2 (https://github.com/markreidvfx/pyaaf2, MIT) and the AAF object specification, DAWproject `Project.xsd`, `MetaData.xsd` and the Java `Timeline` and `Clip` sources (https://github.com/bitwig/dawproject), and ptformat (https://github.com/zamaudio/ptformat) for the Pro Tools header.

**Signatures.** Pro Tools `.ptx` and `.ptf` must start with byte `0x03` or hold the 16-character bit string `0010111100101011` at offset 1 of the first 256 bytes, which is the check ptformat applies for Pro Tools 5 to 12. Pro Tools session version is not extracted, because reading it needs the session de-obfuscated and no real session was available to test that. No source confirms a `.bwproject` or `.reason` header (the published Reason signature belongs to the older `.rns`), so those two accept any content.

## Audio measurements

The audio adapter opens any file libsndfile decodes and streams it in blocks, so memory stays flat for long files. Sample peak, RMS, crest factor and the full-scale sample count are exact for the decoded samples. Loudness follows ITU-R BS.1770-4 and EBU R128: K-weighting derived for the file's sample rate, 400 ms momentary and 3 s short-term windows, gated integrated loudness and EBU Tech 3342 loudness range. Every channel is weighted 1.0, so surround files carry a `channel_weighting` diagnostic. True peak uses 4x polyphase oversampling (2x above 96 kHz) and can under-read by up to about 0.3 dB. Files shorter than 400 ms, silence, or rates below 8 kHz give null loudness with `loudness_unmeasurable`.

MP3, Vorbis and Opus are decoded by libsndfile. Their signal measurements describe the decoded audio, carry confidence `medium` and a `lossy_decode` diagnostic, because decoding can raise sample peaks and codecs add delay and padding.

Band energy uses six bands: sub below 60 Hz, low 60 to 250 Hz, low_mid 250 to 500 Hz (the usual mud region), mid 500 Hz to 2 kHz, high_mid 2 to 6 kHz, and high above 6 kHz. Band energy, spectral centroid, stereo correlation and side-to-mid ratio are whole-file averages. The pitch-class profile is measured energy per pitch class. The profile and the tempo estimate average per-channel FFT magnitudes, so inverted channels do not cancel; files with more than 8 channels are first averaged into 8 groups (channel i into group i mod 8), which bounds the cost and is stated in the confidence reason. `audio.tempo_estimate` and `audio.key_estimate` are `inferred` with confidence `low`: tempo candidates may be half or double the felt tempo, and the key estimate correlates with major and minor profiles only, so modal or pentatonic music (for example Hirajoshi) can be mislabelled. Use the pitch-class profile to reason about such scales. Inferred estimates never raise automatic conflicts.
